# SiteArchitect 11 — інтерактивна практична робота

**Тема:** «Інформаційна структура сайту. Архітектура даних та логіка вебдизайну»  
**Клас:** 11  
**Формат:** вебзастосунок (GitHub Pages + Supabase)

## Що вміє сайт

- Вхід учня за email і паролем; під час реєстрації записуються ім’я, прізвище та клас.
- Кожен учень створює **декілька власних** проєктів, зберігає чернетки й здає готову роботу.
- П’ять навчальних етапів: **паспорт → контент → групування → дерево → результат**.
- Шаблони: портфоліо, освітній ресурс, магазин, блог; можна почати з порожнього проєкту.
- Сторінки: назви, описи та окремі блоки контенту.
- Категорії/папки: вкладеність, переміщення, порядок, автоматичні шляхи HTML-файлів.
- Автоматичне дерево SVG, експорт у **PNG**, а також **JSON**.
- Перехресні переходи для гібридної/мережевої архітектури.
- Аналіз: загальна повнота, опис сторінок, блоки, порожні папки, повторення назв, глибина переходів, нерівномірне наповнення.
- Учитель бачить **усі** роботи у власному кабінеті, фільтрує за класом/статусом, шукає за ім’ям, переглядає повний проєкт, завантажує PNG/JSON/реєстр CSV.
- Після налаштування Supabase: **учень має доступ тільки до своїх проєктів; учитель може переглядати проєкти всіх**. Захист реалізовано на рівні Postgres Row Level Security, а не прихованих кнопок.

## 1. Перегляд без сервера

Відкрийте `index.html` у браузері або опублікуйте файли на GitHub Pages з порожнім `config.js`. Буде показано **деморежим**. Можна вводити ім’я, клас, створювати й редагувати структуру, завантажувати PNG. Проєкти зберігаються лише у `localStorage` цього браузера. Деморежим **не забезпечує приватності, синхронізації або передачі вчителю**. Використовуйте його тільки для ознайомлення.

> У деморежимі зовнішні сервіси не потрібні. Шрифт Manrope із Google Fonts — необов’язковий, є системний резерв.

## 2. Підключення бази Supabase

1. У [Supabase](https://supabase.com/) створіть новий проєкт.
2. Відкрийте **SQL Editor**, вставте весь вміст `schema.sql` і виконайте його. Створяться таблиці `profiles` і `site_projects`, тригер створення профілю, функція визначення ролі та правила **RLS**.
3. Перейдіть у **Project Settings / API** (інтерфейс може змінюватися), скопіюйте:
   - **Project URL**, наприклад `https://abc123.supabase.co`;
   - **Publishable key** або **legacy anon key**.
4. У `config.js` заповніть ці два значення:

```js
window.SITEARCHITECT_CONFIG = {
  supabaseUrl: "https://YOUR_PROJECT.supabase.co",
  supabasePublishableKey: "YOUR_PUBLISHABLE_OR_ANON_KEY"
};
```

5. **Ніколи не вставляйте в `config.js` secret key / service_role key або пароль до бази.** Цей файл буде загальнодоступним на GitHub. Відкритий publishable key — нормальна модель Supabase за правильно налаштованого RLS.

## 3. Авторизація учнів: важливе налаштування

За замовчуванням Supabase може вимагати **підтвердження електронної пошти**. Для реальних учнівських адрес у робочому режимі потрібен налаштований **custom SMTP** (або інша підтримувана система надсилання листів). Вбудований сервіс Supabase не призначений для масової шкільної реєстрації й має дуже жорсткі обмеження.

- **Рекомендований режим:** email + пароль, email-підтвердження увімкнене, налаштований власний SMTP. Налаштуйте `Authentication → URL Configuration → Site URL` на адресу GitHub Pages та додайте її до `Redirect URLs`.
- **Лише для закритого тестування:** тимчасово вимкніть `Confirm email` у `Authentication → Providers → Email`. Це спрощує випробування, проте **не підтверджує, що людина володіє вказаною адресою**, тому не варто використовувати таку конфігурацію для роботи з реальними персональними даними учнів.
- Для відновлення пароля через пошту також потрібне надсилання email (SMTP).

Реєстрація зберігає `full_name` і `class_name` у таблиці `profiles`. За замовчуванням кожен новий обліковий запис має роль **student**.

## 4. Як створити доступ учителя

1. Зареєструйте **власний** акаунт на сайті як звичайний користувач із вашою email-адресою.
2. У Supabase → **SQL Editor** виконайте (підставте вашу адресу):

```sql
update public.profiles
set role = 'teacher'
where id = (
  select id from auth.users
  where email = 'TEACHER_EMAIL@example.com'
);
```

3. Вийдіть із сайту й увійдіть знову. Відкриється **кабінет учителя**.
4. Студенти самостійно змінити роль на teacher **не можуть**: для браузерного API заборонене оновлення стовпця `role`.

## 5. Публікація на GitHub Pages

1. Створіть новий репозиторій на [GitHub](https://github.com/new), наприклад `sitearchitect-11`.
2. Завантажте файли **із папки проєкту**, щоб `index.html` опинився в **корені репозиторію**:
   - `index.html`, `styles.css`, `app.js`, `boot.js`, `config.js`, `favicon.svg`;
   - `schema.sql` і документацію можна лишити в репозиторії, вони не містять паролів.
3. Відкрийте **Settings → Pages → Build and deployment → Source: Deploy from a branch**.
4. Оберіть гілку `main` та каталог `/(root)` → **Save**.
5. Сайт буде доступний приблизно за адресою `https://USERNAME.github.io/sitearchitect-11/` (точна адреса показана у Pages).
6. Якщо ввімкнене підтвердження пошти, додайте повну URL-адресу сайту до Supabase **Authentication → URL Configuration**.
7. Відкрийте сайт з обліковими записами двох учнів і вчителя та перевірте права.

> GitHub Pages хостить лише статичний фронтенд. Без Supabase неможливо реалізувати безпечне збереження та розмежування доступу до робіт.

## 6. Рекомендований наскрізний тест доступу

1. Створіть `student-a` і збережіть від його імені проєкт А.
2. Вийдіть, увійдіть як `student-b`. Акаунт Б **не повинен** бачити проєкт А; прямий запит до таблиці теж має бути обмежений RLS.
3. Увійдіть як teacher і перевірте, що у вкладці «Лише здані» проєкт з’являється **після натискання «Здати роботу»**.
4. Перевірте PNG-експорт та CSV-реєстр.
5. Переконайтеся, що учень не може змінити `role` або `owner_id` через API.

## 7. Перелік файлів

| Файл | Для чого |
|---|---|
| `index.html` | Вхідна вебсторінка |
| `styles.css` | Адаптивний дизайн |
| `app.js` | Інтерфейс, конструктор, перевірка, експорт, робота з базою |
| `boot.js` | Підключення Supabase JS лише в онлайн-режимі |
| `config.js` | URL та **публічний** ключ вашого проєкту |
| `schema.sql` | База даних, ролі та захищений доступ |
| `favicon.svg` | Значок вебзастосунку |
| `ЗАВДАННЯ_ДЛЯ_УЧНІВ.md` | Готове формулювання домашнього завдання |

## 8. Педагогічні умови й безпека

Сайт зберігає ім’я, прізвище, клас та навчальні результати як персональні дані. Перед використанням у школі потрібні належна підстава обробки, інформування учнів/батьків відповідно до вимог закладу й чинного законодавства, правила термінів зберігання та доступу. Не робіть публічними таблиці БД і не завантажуйте базу з персональними даними в GitHub-репозиторій. Для повністю закритого шкільного рішення можна замінити реєстрацію на адміністраторське створення облікових записів.

Автоматична «готовність %» — навчальний чекліст, **не оцінка за 12-бальною шкалою**. Орієнтир «до 3 кліків» використаний із навчальної презентації як евристика, не універсальна вимога UX/SEO.
